Integrations are chosen at install: tick them in the app, or pass them to the unfr0zen command-line tool. To change them, run the install again.

MQTT

Wi-Fi, to your MQTT broker. Home Assistant discovers the thermostat there.

Matter

Wi-Fi or Thread, to a Matter controller: Apple Home, Google Home, Alexa or Home Assistant.

Zigbee

The thermostat's own 802.15.4 radio, to your coordinator: Zigbee2MQTT or ZHA.

External temperature

A thermometer of yours regulates the heating in place of the thermostat's own sensor.

nestlocal replaces the thermostat's connection to Nest's cloud. Nest's own nlclient keeps running the screen and the heating, pointed at nestlocal on the unit instead of Nest's servers. The Nest and Google Home apps no longer control the thermostat; Home Assistant does, over your network. Remaining traffic to Nest's and Google's servers, NTP for example, stops with Block Nest and Google servers.

  • nestlocal. MQTT, Matter, Zigbee, home screen themes and Doom are served by nestlocal, which any of them installs on the thermostat.
  • Wi-Fi. MQTT and Matter use Wi-Fi, joined from the thermostat's Settings → Network. The network doesn't need internet access.
  • Generations. 1st, 2nd and 3rd generation. The 1st has MQTT, Matter over Wi-Fi and the external temperature: no Zigbee or Matter over Thread (its radio is on a UART), and no USB shell. The Nest Thermostat E is detected and refused.
  • Command line. On Linux and macOS, the app's executable run with arguments; Windows has the app only.
  • Linux. Run the app and CLI as your normal user, after the one-time USB permission setup. Run logs: ~/.local/share/unfr0zen/logs/, or $XDG_DATA_HOME/unfr0zen/logs/ when set.
  • Your own integration. The MQTT topics, Zigbee clusters and Matter endpoints are documented under Protocols.

Settings menu

The thermostat's settings menu gets an entry for each installed feature, right after its first entry: ZIGBEE (pairing with a 30-second countdown), MATTER (pairing), THEMES (the home screen themes, 3rd generation), DOOM and UPDATE (Changes over Wi-Fi). UNFR0ZEN, with the version that set the thermostat up, takes LEGAL INFO's place before RESET. NEST APP, SOFTWARE, NEST PRO, LOCK, the energy partner entry (utility, which Nest's servers run) and LEGAL INFO leave the menu. Each entry opens its page; Back returns to the menu.

The screens are linked into the unit's own nlclient; the original is kept at /etc/unfr0zen/nlclient.original across installs (on the 3rd generation at /media/scratch/.unfr0zen/backup/nlclient.original). Supported versions and undo: platform/common/nlclient/README.md.

The thermostat connects over Wi-Fi to your MQTT broker (the Mosquitto add-on, for example); Home Assistant's MQTT integration discovers and controls it there. The broker is the only intermediary. Port 1883, or 8883 with TLS; a password needs a user; a CA certificate turns on TLS.

Names in Home Assistant

Home Assistant shows the thermostat as a device named Nest Thermostat, with entity IDs like climate.nestlocal_<serial>_thermostat. A device name and an entity ID root replace them:

  • Device name. Nest FamRm for example: one line of at most 32 bytes, the same as Matter's.
  • Entity ID root. nest_famrm for example: lowercase letters and digits, words joined by _, at most 64 characters. It gives climate.nest_famrm_thermostat, sensor.nest_famrm_current_temperature.
  • <serial> in either stands for the thermostat's 16-character serial, which counts towards the limit (lowercase in the root, kikoo_<serial>_lol for example).

Left empty, the thermostat keeps the names it has, so installing again for an update changes nothing. With a new root, Home Assistant (2025.10 or later) moves the thermostat's entities to the new IDs, with their history and what was set on them there (names, areas, icons); automations and dashboards need the new IDs. If Home Assistant isn't running when the thermostat connects after the install, the IDs change the next time it starts.

Updates

An unfr0zen update entity shows the version the thermostat runs and, when it can reach GitHub, the latest release, checked every 6 hours. On a 3rd generation unit Install downloads that release's bundle, checks it against its manifest and unfr0zen's release key, installs it and restarts the thermostat. Only official releases install, and never one older than the installed version, unless Allow unsigned updates was on when the unit was set up. 1st and 2nd generation units show the versions; update them with the app. An install that fails says why in the thermostat's log and leaves it running; one that does not come back after the restart is fixed by setting it up again with the app over USB.

A thermostat that can't reach GitHub installs a release's bundle (unfr0zen-diamond3-<version>.tgz, from the release's assets) from your own network: put it on any web server the thermostat reaches and publish its URL, for example from a Home Assistant script:

action: mqtt.publish
data:
  topic: nestlocal/<serial>/set/update
  payload: http://nas.lan/unfr0zen-diamond3-v0.5.0.tgz

Weather and clock

Two Home Assistant blueprints replace what Google supplied. Both need MQTT; on Zigbee, see Zigbee.

Weather

Sends outdoor temperature, humidity, conditions and forecast every 15 minutes, when Home Assistant starts, and when the weather entity comes back from unavailable or unknown.

Import it, create an automation, pick the thermostat and a weather entity. Outdoor sensors are optional; °F is converted to °C.

Clock

On a network without NTP access, Home Assistant answers the thermostat's time requests.

Import it and create an automation; no settings, answers every thermostat.

Matter

AppCLI
Matter, under Set up → Integrations--matter
Pairing code--matter-code CODE
Device name, under Home Assistant--device-name NAME

Works alone or beside MQTT; needs Wi-Fi. The device name, shared with MQTT, is the name controllers show: Matter's node label, at most 32 bytes, <serial> standing for the serial. An install that gives a new one sets it; a name changed in the controller stays until then.

Pairing

Pairing code 0347-100-5534, or one of your own with a valid check digit; --matter-code turns on Matter. The first pairing window opens by itself: UNFR0ZEN → Matter shows Ready to pair with the QR and code, then Paired.

  1. Home Assistant: Settings → Devices & services → Add integration → Matter.
  2. Add the device with the pairing code, or scan the QR shown on the thermostat.
nestlocal uses the Matter test vendor ID (0xFFF1) and test attestation, so controllers treat it as uncertified. Home Assistant's Matter server accepts it only with its test-net DCL option on.

Enable pairing → Forget and pair forgets every Matter controller before opening a new window. This cannot be undone, even if the new pairing fails; Wi-Fi and Zigbee settings are kept.

Entities

Home Assistant gets the thermostat (modes, setpoints and range, action, eco as a preset, humidity, outdoor temperature), occupancy, °C/°F, backplate temperature, battery, fan and its timer, the fan schedule's run time, start and end, and switches for Auto-Schedule, Home/Away Assist, Sunblock, Early-On, the eco limits and, with a humidifier or dehumidifier, humidity control, and with hot water control, Hot water boost (30 minutes when on) and Hot water schedule, and with an air filter, the filter reminder and a Filter reset switch that resets the filter when turned on, and with a fan, the fan schedule. The other MQTT entities aren't offered over Matter.

Bluetooth commissioning

3rd generation units with the supported DA14580 Bluetooth firmware also pair over Bluetooth; nestlocal loads the unit's own radio firmware into RAM, the stock image unchanged. Bluetooth advertises only while the pairing window is open; traffic goes over Wi-Fi or Thread. The thermostat's own Bluetooth is turned off for it: real Nest Temperature Sensors stop working, and the Nest app cannot pair with it over Bluetooth. Other units pair over IP.

Sleep

Experimental. The thermostat sleeps between Matter messages and wakes for a controller's: unicast UDP to port 5540, and on the 3rd generation also a DNS-SD lookup of the unit and an IPv6 neighbour solicitation for its addresses. nestlocal adds these to the wake patterns Nest's sleep daemon gives the Wi-Fi chip. The 1st and 2nd generation's chip lets no multicast through while the unit sleeps, so it answers lookups when it wakes on its own. Each wake reports to the controllers' subscriptions, which they keep through its sleep. It stays awake while commissioning. With more fabrics than the chip has room for, lookups of other Matter devices wake it too.

Matter over Thread

AppCLI
Thread support, under Matter--matter-thread

The thermostat joins a Thread mesh as a router and serves Matter over it, beside Wi-Fi; the commissioner supplies the credentials. Needs Matter. Takes the radio from Nest's Thread firmware (Heat Link), so not with Zigbee. On the 2nd generation nestlocal flashes a Thread image and keeps the unit awake while Thread runs. Design and device details: platform/common/radio/thread/README.md.

Zigbee

AppCLI
Zigbee, under Set up → Integrations--zigbee

A Zigbee router on the thermostat's own 802.15.4 radio, alone or beside MQTT and Matter. On first start nestlocal replaces Nest's Thread firmware (Heat Link) with its own; installing again without Zigbee puts Nest's back. Transmit power is Nest's -15 dBm.

Heat Link models

A 3rd generation Heat Link model (Display-3.x, Display-5.x) on firmware 6.4-8 can stop on H71 or H74 once the Heat Link can't connect. With Zigbee or Thread, Works With Nest boiler (--wwn-boiler) sets the unit up as heating a Works With Nest boiler: it keeps heating through W1 with its safety temperature and real backplate sensors, and Zigbee, Matter and MQTT offer heat. Off unless chosen; installing again without it takes it back. While set: Safety Temp shows a notice (its values stay in force), Heating Equipment does nothing, Pro Setup's boiler pages go nowhere, and with nothing on W1 the boiler has to be driven from the setpoint, with a relay from Home Assistant for example.

Coordinators

Any Zigbee 3.0 coordinator works: standard clusters, so ZHA needs no quirk (its switches need zha 0.0.61, June 2025, or later). Zigbee2MQTT with the converter is recommended: it names every entity and carries the weather.

  1. Zigbee2MQTT 2.12.1 or later: copy nest-learning-thermostat.mjs to data/external_converters/ and restart Zigbee2MQTT.
  2. Permit join on the coordinator. The thermostat joins the strongest network permitting joins, on any channel, and keeps it across restarts.
  3. After updating the converter, re-interview the device to refresh its generation-specific model, then Reconfigure it so Home Assistant gets the new entities.

The switches are Binary Output clusters, so ZHA names them. A thermostat paired on an older release has to be paired again in ZHA, or re-interviewed in Zigbee2MQTT with the updated converter; delete the old switch entities.

Entities, clock and weather

With the converter, Home Assistant gets the MQTT entities under the same names, minus IP address and Wi-Fi signal; temperature and HVAC action sit on the climate entity. The clock comes from the coordinator's Time cluster, no blueprint needed. The weather has a Zigbee2MQTT blueprint: import it, create an automation, pick the thermostat, the base topic (default zigbee2mqtt) and a weather entity. Outdoor sensors are optional; °F is converted to °C. Nothing needs Wi-Fi.

Joining and moving networks

On a coordinator with per-device keys, a router needs its own trust-centre link key to help others join. If the thermostat still has only the global key, enable pairing again.

To move networks: UNFR0ZEN → Zigbee → Enable pairing. The thermostat leaves its network, forgets its credentials and looks for one permitting joins for 30 seconds; on timeout it stays off any network until pairing is enabled again or nestlocal restarts.

Sleep

The radio routes while the thermostat sleeps and wakes it for a message, on the 2nd generation's kernel and the 3rd generation's 5.8 to 6.1 kernels; on others, messages wait until the unit wakes. The 2nd generation doesn't sleep with a USB cable connected.

External temperature

AppCLI
External temperature, under Set up → Integrations--external-temperature

A thermometer of yours regulates the heating in place of the thermostat's own sensor. Every generation, with MQTT, Matter or Zigbee. nestlocal presents a virtual Nest Temperature Sensor (gen 1 and 2: local sensor input, on Nest firmware 5.9.4-5; gen 3: Bluetooth). Send readings and the thermostat regulates from them; stop, and it goes back to its own sensor.

  • One sensor. Only one external temperature is supported for now.
  • Named after the thermostat's room. The sensor takes the thermostat's room, so the Sensors menu lists it under that room's name, Living room for example. It cannot be renamed on its own yet.
  • On 3rd generation, Bluetooth is turned off. The thermostat no longer hears real Nest Temperature Sensors, and the Nest app cannot pair with it over Bluetooth.

Setting it up in Home Assistant

Install with the option and your integration, then import that integration's blueprint and create an automation. Each sends the reading on change, every 10 minutes and when Home Assistant starts; °F is converted to °C; nothing is sent while the thermometer is unavailable.

MQTT. Import external-temperature-mqtt.yaml, create an automation from it, and pick the thermostat (its MQTT device) and your room temperature sensor. It publishes each reading to nestlocal/<serial>/set/external_temperature.

Zigbee2MQTT. Use the converter from Zigbee. After updating it, re-interview the thermostat, then Reconfigure it, so Home Assistant gets Temperature source. Import external-temperature-zigbee.yaml, create an automation from it, and pick the thermostat, the Zigbee2MQTT base topic (default zigbee2mqtt) and your room temperature sensor. It publishes {"external_temperature": 21.5} to <base topic>/<IEEE address>/set. There is no blueprint for ZHA: the reading is attribute 0x0005 of the manufacturer-specific cluster 0xFC00 (see Protocols).

Matter. The thermostat's Matter device gets an External temperature select offering 5 to 35 °C in half degrees. Import external-temperature-matter.yaml, create an automation from it, and pick that select and your room temperature sensor. Readings are rounded to the nearest half degree. Choosing the same temperature again counts as a new reading.

How it behaves

  • The sensor appears in the Sensors menu when the thermostat starts. The thermostat uses its own sensor until the first reading arrives.
  • A reading counts for 30 minutes, repeated to the thermostat every minute. About 11.5 minutes after it lapses, the thermostat goes back to its own sensor until the next reading.
  • Choosing the backplate in the Sensors menu lasts until the thermostat restarts. After a restart, the next reading switches it back to the external temperature.
  • Home Assistant shows External temperature, the reading while it counts, and Temperature source, external or backplate. Zigbee2MQTT shows Temperature source only. On Matter both are selects: Temperature source shows the source, and choosing the other one is refused.
  • Installing again without the option removes the sensor from the thermostat, its Sensors menu entry included, and undoes the gen 1 and 2 input patch or restores the gen 3 Bluetooth setting.

Changes over Wi-Fi

AppCLI
Changes over Wi-Fi, under Set up → Features → Remote access--update-api
Connect over Wi-Fi on Set up → Connect, then Update on Reviewunfr0zen --wifi IP, with the setup options
None: Update sends this app's nestlocal with the settingsunfr0zen nestlocal-update --host IP
The unit's settings, read into the steps by Connect over Wi-Fiunfr0zen nestlocal-update --host IP --show
Force older nestlocal, under Review → Developer options while connected--force

Lets a newer unfr0zen change a thermostat it set up over Wi-Fi, without USB: replace its nestlocal, or send the Set up page's settings, which change the options and the files they need. Needs MQTT, Matter or Zigbee, beside which nestlocal keeps the unit awake while the update window is open, while a new set is on trial, and for 60 seconds after each connection to its update port. Any device on the network can extend that by connecting again, which costs battery only on a thermostat without a C wire. nestlocal then listens on TCP port 8443 of the unit. It takes a change only after someone allows it on the thermostat and enters the code the screen then shows, or from a laptop that was trusted that way before.

What a Wi-Fi run can change. Everything on the Set up page that is a file on the unit's root or scratch volume: the root password, NTP server, MQTT, Matter and Zigbee settings, the device name and entity ID root, external temperature, the backplate simulator, the home screen themes, Doom, the blocked cloud, SSH and its key, unsigned updates and the nestlocal binary itself. A Wi-Fi run produces the same files as the same settings over USB, the run's record of them (/etc/unfr0zen/options.json) included, so a later release update installed from Home Assistant keeps the settings sent over Wi-Fi.

What stays USB-only. The kernel, the boot loaders, the boot slot and the NAND layout. On a 1st or 2nd generation the USB shell and dark theme also choose the kernel and its boot order, so they change over USB only; the Set up page shows them as the unit has them. nestlocal and the update API have to stay on, so removing them needs USB too, as does a NAND backup. If a change goes wrong, a USB install always recovers the unit. A thermostat set up before unfr0zen kept its files on the scratch volume needs one USB setup before its next Wi-Fi update, since its nestlocal can't move them there: the app says so on Connect and Review and keeps Update off, and unfr0zen --wifi stops before sending anything; unfr0zen nestlocal-update still replaces its nestlocal.

  1. In the app, on the Set up page's first step, Connect, enter the thermostat's address (your router lists it) under Or over Wi-Fi and press Connect over Wi-Fi; or run unfr0zen nestlocal-update --host IP --show. The app first sends a packet to wake the unit, then asks to update it.
  2. The thermostat wakes and asks, full screen, Update from NAME (IP)? with Allow, Allow and trust and Deny; turn the ring and press. After either Allow it shows an 8-digit code, which you enter in the app (the screen has a Hide choice if you want the thermostat back). The window the code opens lasts 10 minutes and takes one change. The app reads the unit's settings into the steps and shows, under the address, the unit's generation, the nestlocal it runs and the one this app sends, so you can see whether it is behind. The root password is not read back: leave it blank to keep the unit's. The SSH key and the MQTT CA certificate show as the thermostat's, sent back unless you clear or replace them.
  3. While connected, the steps go on without USB and Review ends on Update instead of the setup and its backup. Change what you want and press it: it sends the form with this app's nestlocal, so it also updates nestlocal; with nothing to change, it says so. Enter the same code again: it stays on Settings → UPDATE while the window is open, and once the window has closed the thermostat asks again and shows a new one. A laptop allowed with Allow and trust needs no code: its read closed the window, and it is trusted from then on. The app lists the changes and whether the unit will restart nestlocal or reboot; confirm, and it sends them as one set, then waits until the unit keeps it or rolls it back.
  4. Press Disconnect on Connect to put the steps back as they were before connecting; the flow then sets it up over USB again.

From the command line, unfr0zen --wifi IP takes the setup options as the unit's full settings, like a USB run, except that a missing --root-password keeps the unit's. --code CODE gives the code instead of typing it when asked (a trusted laptop needs neither, so a script run outside a terminal can leave it out), --dry-run only lists the changes, and --force allows an older nestlocal than the unit's. Options for the USB run (--nand-image, --entry-point, --device) are refused with --wifi. unfr0zen nestlocal-update --host IP still sends only the nestlocal binary; the app has no such step, since Update always sends nestlocal with the settings. It is a developer command: the unit's unfr0zen version (/etc/unfr0zen/version and the record in /etc/unfr0zen/options.json) stays as it was, so Home Assistant's update entity still shows the old version, and a release update may replace that nestlocal, even with an older one. Update in the app and unfr0zen --wifi keep the versions in step.

Or start at the thermostat: Settings → UPDATE → Allow update (or Allow and trust) opens the window, shows the code and the address, and keeps the screen lit. Then start the run, with the CLI's --code CODE or entering the code when asked.

The prompt. A prompt nobody answers within 60 seconds counts as Deny. After 3 prompts in a row that were denied or unanswered, the thermostat stops raising them until someone presses Allow update (or Allow and trust) on Settings → UPDATE, or the unit reboots; merely opening the page does not. While another update holds the unit, a new request is refused as busy.

Trusted laptops. Allow and trust makes the laptop trusted as soon as the app has proved it holds the code (its first request in that session), even if the update then fails or is cancelled. The unit keeps up to 4 laptops. Trusting a laptop again replaces its entry rather than adding one: the app proves it still holds the old key, and replaces its own key file only once the unit has kept the new trust. If the thermostat adds the laptop instead, the app says so, and the old entry stays on the list until you forget it. With the list full, only the prompt the app raises offers Allow and trust, and only to a laptop on the list; Settings → UPDATE offers it only while the unit trusts fewer than 4, so forget one there to make room for another laptop. The app keeps a key file for each unit in its data directory (trusted/, readable only by you). A trusted laptop needs no touch at the thermostat: the thermostat wakes and shows Update from NAME and the stage for the whole session, with Cancel. A session that only reads the settings closes once they are read. Each trusted session lasts at most 10 minutes and ends after a minute without a request. While an update window is open, or when the thermostat cannot show the notice, the app uses a code instead, as for a laptop that is not trusted.

  • Cancel acts on the stage the update has reached: it ends the session, discards a set that is still arriving, and after the set was applied rolls it back. The app then reports "Cancelled on the thermostat". Cancelling does not make the unit forget the laptop.
  • While a set is on trial the notice offers Roll back and Hide. After Hide, Roll back stays on Settings → UPDATE until the set is kept or rolled back. The app reports a roll back done there as "Cancelled on the thermostat: the unit put its files back".
  • Forget. Settings → UPDATE → Trusted laptops lists them; choose one and confirm Forget. It takes effect at once and ends that laptop's session. Turning the update API off with a USB run wipes the whole list. A USB run that removes nestlocal altogether leaves the list on the unit, and its trust returns if the update API comes back; forget the laptops first if that matters.
  • A trusted laptop's key file can change everything a Wi-Fi run can, the root password and the SSH key included, without anyone at the thermostat. Keep it private, and forget a laptop on the thermostat when you lose it or stop using it.

Waking. A sleeping thermostat does not answer the network, so the app sends one UDP packet to Matter's port 5540 before each attempt, and the unit wakes. A unit without Matter gets nestlocal's Wi-Fi wake filter with the update API alone, with a pattern for TCP port 8443; this changes what a USB run writes for such a unit, and a Wi-Fi set that adds or removes it reboots the unit.

  • Restart or reboot. A set that changes only nestlocal, its options, its MQTT and device name files and the run's record restarts nestlocal. A set that changes any other file, such as the nlclient patches, the root password or Doom, reboots the unit. The app says which before it sends.
  • Rollback. The unit checks the set before it applies it, keeps the previous files, and proves the result to the app with the session's key. If nlclient (the thermostat's own software) has not reached the new nestlocal before it starts a 4th time, or within 10 minutes, the unit puts every previous file back, and the app reports that the change was rolled back. After a reboot the set is kept only once the unit is also on the network, with an IPv4 address and the update listener up: a set that cuts the unit off from Wi-Fi rolls back by itself. A new set is refused while the previous one is still on trial. What the unit reports after it restarts is not authenticated.
  • The code never crosses the network, and nothing that does lets anyone work it out: the app and the unit use it in a SPAKE2 key exchange, which keys the session, and everything the app reads from or sends to the unit is encrypted with it. Each try at a code takes an exchange with the unit, and five close the window. A code takes one set: if that fails, allow again for a new one. After five wrong codes the unit answers busy to a new request for up to 10 minutes: wait, or press Allow update on the thermostat.
  • The app will not install a nestlocal older than the unit's; Force older nestlocal under Review → Developer options (--force) installs it anyway. The app's Update installs the app's own files with the nestlocal it carries, so it also brings an old unit's files up to date. unfr0zen nestlocal-update, which sends the binary alone, also refuses one that needs files only a newer USB install puts on the unit; its --force sends it anyway.
  • Release updates. A release installed from Home Assistant's update entity is not installed while a set sent over Wi-Fi is on trial or one is being sent; nestlocal's log says why (update: … not installed: …). Keep or roll back the set, or let it finish, then install again. A Wi-Fi change waits as busy while a release installs. nestlocal logs the Wi-Fi update's own lines with wifi-update:.
  • If the window has closed, the app says so: start again, or open the window again on the thermostat. A thermostat that is asleep may not answer: wake it and try again. If nothing at the address takes changes, the unit was not set up with this option.

Backup & restore

AppCLI
Back up unitunfr0zen backup [OUT]
Not availableunfr0zen verify IMAGE
Restore to unit, Restore from fileunfr0zen restore IMAGE
  • Backup. The whole NAND as an image with a .sha256 beside it. On the 3rd generation: 512 MiB, ECC-corrected, with a .bad list of its bad and unreadable blocks. On the 1st and 2nd: raw pages with OOB, unclean blocks read until two reads agree. Nothing is written during a backup.
  • Resume. unfr0zen backup OUT with the same OUT resumes an interrupted backup; the app, and a run without OUT, start a new file.
  • Restore. Verifies the image against the .sha256, asks, then writes it back. On the 1st and 2nd generation the factory-bad blocks must match the chip's, only differing blocks are rewritten, and an interrupted restore is run again.

Home screen themes

AppCLI
Customizable home screen themes, under Set up → Features--themes

3rd generation, on the firmware versions the themes support; another is refused at install. Pick how the home screen's dial looks from UNFR0ZEN → Themes. The choice is kept across restarts.

  • The ring, the button and the menus work as stock: the theme only draws the dial, on the thermostat's GPU, at up to 60 frames a second while it moves.
  • A theme that fails shows the target and its error on the dial; pick another from UNFR0ZEN → Themes. A theme that keeps restarting the display is not started again until you pick it again.
  • Your own themes go in /media/scratch/.unfr0zen/themes (see making a theme); the Themes page shows them within a few seconds.
  • Install again without the option to remove it.

Doom

AppCLI
Doom, under Set up → Features--doom

Installs Doom with the shareware episode (DOOM1.WAD v1.9, included). Start it from UNFR0ZEN → Doom → Play.

  • You walk forward all along. Turn the ring to steer, press it to fire. Doors and switches open as you walk into them.
  • In menus, the ring moves and a press selects.
  • Hold the ring for 3 seconds to quit back to the thermostat.
  • Sound comes from the piezo: the PC speaker effects and each song's highest note.
